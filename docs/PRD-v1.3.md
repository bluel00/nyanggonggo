## 1. 왜

- 상세 화면의 사진이 4:5로 꽉 채워져(cover) 상당 부분이 잘린다. 전체를 보려면 사진을 눌러 전체 보기로 들어가야 한다.
- 기능명세서의 원래 요건은 "비율 유지, 크롭 최소화"였다. 디자인 시스템이 4:5 cover로 정하면서 상세 화면도 그 규칙을 따르게 됐다.
- 사진 감상이 이 서비스의 핵심이다.

## 2. 실측 (2026-10-08, 공고 293건, 사진 583장)

| 사진 비율(가로/세로) | 비중 | 4:5 cover에서 잘리는 면적 평균 |
|---|---|---|
| 1.15–1.4 (4:3 가로) | 49.7% | 39.9% |
| 0.7–0.85 (3:4 세로) | 36.4% | 6.1% |
| 0.85–1.15 (정사각 근처) | 10.1% | 18.4% |
| 0.7 미만 또는 1.4 초과 | 3.8% | 30.9~44.6% |

- 서울·경기는 가로 사진이 대부분이라 잘림이 크다(평균 36% / 27%). 부산·대구는 세로가 많다(13~14%).
- 공고당 사진은 98%가 2장이다. 같은 공고 안에서 비율이 섞인 경우가 13%다.
- 공공 API는 사진 크기를 주지 않는다.

## 3. 요구사항

- 상세 화면의 사진은 잘리지 않는다.
- 사진 칸의 비율은 그 공고의 **첫 사진 비율**을 따르되, 3:4~4:3 범위로 제한한다.
- 같은 공고의 모든 사진은 그 칸 안에 잘리지 않게(contain) 들어간다. 빈 곳은 페이지 바탕색이다. 넘겨 볼 때 칸 높이는 바뀌지 않는다.
- 첫 사진의 크기는 서버가 미리 읽는다. 결과는 사진 URL별로 캐시한다(크기는 바뀌지 않는다).
- 크기를 제때 알 수 없으면(시간 초과, 실패) 칸은 1:1로 그린다.
- 사진이 로드되면서 화면이 밀리지 않는다.

## 3-1. 목록 카드 (추가, 2026-10-12)

- 목록 카드 사진은 1:1, 가운데 기준으로 채운다(cover). 로딩 카드도 1:1이다.
- 이유: 4:5에서는 가로 사진의 양옆이 잘려, 동물이 한쪽에 있으면 머리·얼굴이 잘렸다. 공고 60건을 비교해 실제 비율 분포로 가중하면 머리·얼굴 잘림이 약 10.5%에서 2.8%로 줄었다.
- 검토하고 뺀 방식: 사진 내용을 보고 자르기(sharp attention/entropy)는 철창·글씨 쪽으로 쏠려 현행보다 나빴다. 4:3 칸은 머리는 자르지 않았지만, 세로 사진의 60%와 정사각 사진의 70%에서 귀·발을 잘랐다(실제 비율 분포로 가중하면 전체의 약 29%).
- 카드는 사진 크기를 읽지 않는다. 목록과 상세 첫 사진이 같은 프록시 주소를 그대로 쓴다.
- OG 이미지는 4:5를 유지한다.

## 4. 진행 조건 (게이트)

- 크기 읽기가 상세 화면 응답을 늦추는 정도를 배포 환경(icn1)에서 잰다.
- 기준 (배포 전 확정, 2026-10-08):
  - 처음 방문(크기 캐시 없음) 상세 응답 시간 증가가 중앙값 150ms 이하
  - 크기를 못 읽어 1:1 칸으로 나온 비율이 10% 이하
  - 시간 초과 상한은 300ms다.
- 둘 중 하나라도 넘으면 이 방식 대신 "칸 1:1 고정 + contain"으로 간다.
- 측정: 저장소 밖 `image-ratio/gate2.mjs`로, 한 번도 열지 않은 공고의 처음 방문 30건을 모은다. 공고마다 처음 방문과 바로 다시 연 시간의 차이를 크기 읽기로 늘어난 시간으로 본다.

- 결과 (2026-10-12, 새 공고 30건, 지역 5곳·개/고양이·보호중/종료):
  - 크기 읽기로 늘어난 시간(처음 − 다시) 중앙값 106.5ms (90번째 181ms) → 통과
  - 크기를 못 읽어 1:1로 나온 칸 0/30 → 통과. 표본이 작아 95% 신뢰구간 상단은 11.4%다.
  - 1:1로 보인 2건은 실제 정사각 사진이었다(대체 칸 아님).
  - 처음 방문이 1.3초를 넘은 3건은 칸이 제 비율로 나왔다. 크기 읽기가 아닌 다른 원인(콜드 스타트 추정, 미확인)이다.
- 이후: 대체 칸이 잦아지는지 서버 로그 `image size unavailable`로 지켜본다.

## 5. 비범위

- OG 이미지(4:5 cover 유지). 목록 카드는 3-1절에서 따로 정했다.
- 저해상도 사진(짧은 변 480px 미만 27.6%)의 흐림. 사진 자체의 한계다.
- 전체 보기(현행 유지).

## 6. 결정 기록

| 항목 | 결정 | 이유 |
|---|---|---|
| 상세 사진 | 첫 사진 비율(3:4~4:3) 칸 + 전부 contain | 원래 요건 "비율 유지, 크롭 최소화"를 거의 그대로 지킨다. 고정 칸 + contain은 평균 18~24%가 여백이다 |
| 크기를 모를 때 | 1:1 칸 | 가로·세로 사진 모두 여백 25%로 고르다 |
| 목록 카드 (2026-10-08) | 4:5 cover 유지, 따로 검토 | 피드는 크기 균일이 중요하다 |
| 목록 카드 (2026-10-12) | 1:1 cover, 가운데 | 머리·얼굴 잘림 약 10.5% → 2.8%. 크기는 고르게 유지 |
| 게이트 기준 | 첫 방문 증가 중앙값 150ms 이하, 1:1 대체 10% 이하 | 결과를 보기 전에 숫자로 정해 둔다 |
| 게이트 판정 (2026-10-12) | 통과, 현재 방식 유지 | 증가 중앙값 106.5ms, 1:1 대체 0/30 |
| 로딩 뼈대의 뒤로가기 | 앱 안에서 왔으면 뒤로가기, 바로 들어왔으면 버튼 없이 자리만 | 뼈대는 공고를 몰라 기본 목록으로 가던 문제 (구현 중 발견) |
