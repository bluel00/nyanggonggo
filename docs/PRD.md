---

- 문서명: PRD – 유기묘 공고 모바일 웹
- 버전: v1.0 (Final)
- 대상: 사이드 프로젝트 / 포트폴리오
- 범위: MVP 기준

---

## 1. 제품 개요

### 1.1 배경

유기동물 공고는 공공데이터로 제공되고 있으나,  
대부분 앱 설치를 요구하거나 UX가 불편한 웹을 통해서만 접근 가능하다.

특히 고양이 공고는 **사진 중심으로 가볍게 소비·공유될 수 있는 콘텐츠**임에도,  
기존 서비스들은 정보 중심 설계에 머물러 있어  
잠재 사용자들이 자연스럽게 유기묘 정보를 접할 기회를 놓치고 있다.

---

### 1.2 문제 정의 (Problem Statement)

유기묘 공고 정보는 존재하지만,

- 접근성이 낮고
- 사진 감상이 불편하며
- 공유 시 맥락 전달이 어렵다

그 결과, **입양 의사가 없던 사용자에게도 노출될 수 있는 기회 자체가 제한**되어 있다.

---

### 1.3 제품 목적

- 설치 없이 누구나 유기묘 공고를 쉽게 볼 수 있게 한다
- 사진 중심 UI로 공고를 **편하고 예쁘게** 제공한다
- 가벼운 공유를 통해 더 많은 사람에게 자연스럽게 노출되도록 한다

---

### 1.4 가치 제안 (Value Proposition)

> **설치 없이, 유기묘 공고를 사진 중심으로 가장 편하고 예쁘게 볼 수 있는 모바일 웹**

---

## 2. 대상 사용자

### 2.1 Primary Persona

**고양이 사진을 좋아하는 모바일 사용자**

- 연령: 20~30대
- 디바이스: 모바일 중심
- 특징
    - SNS·메신저 사용 빈도 높음
    - 귀엽거나 인상적인 콘텐츠를 보면 공유함
    - 앱 설치에는 보수적

**Needs**

- 예쁜 고양이 사진을 빠르게 보고 싶다
- 현재 상태(보호중/종료)를 한눈에 알고 싶다
- 마음에 드는 고양이를 쉽게 공유하고 싶다

**Pain Points**

- 기존 유기동물 서비스는 앱 설치가 필요함
- 디자인과 UX가 불편함
- 공유 시 정보 맥락 전달이 어려움

---

### 2.2 Secondary Persona (0.5)

**입양을 고려하며 정보를 탐색하는 사용자**

- 지역, 보호 상태, 종료일을 중요하게 봄
- 필터를 활용한 탐색 니즈가 있음

---

## 3. 사용자 흐름

### 3.1 Service Flow

text

```text
서비스 진입
 → 고양이 목록
   → 필터 적용
     → 고양이 상세
       → 이미지 크게 보기
       → 찜
       → 공유 (카카오톡 / 링크)
```

---

### 3.2 User Workflow

#### Workflow A – 감상 & 공유 (핵심)

1. 공유 링크 또는 직접 진입
2. 고양이 목록 스크롤
3. 마음에 드는 카드 선택
4. 사진 크게 감상
5. 카카오톡으로 공유

#### Workflow B – 탐색

1. 고양이 목록 진입
2. 필터 열기
3. 조건 선택 후 적용
4. 결과 확인
5. 상세 페이지 진입

---

## 4. 기능 요구사항

### 4.1 핵심 기능 (MVP)

#### 1) 고양이 목록 조회

- 공공데이터 API 기반
- 디폴트 축종: 고양이
- 카드형 UI, 사진 중심
- 무한 스크롤 방식
- 우선순위: 상

---

#### 2) 필터 기능

- 축종 (고양이/강아지)
- 지역
- 보호 상태 (보호중/종료/전체)
- 정렬 (최신순 / 종료임박순)
- 바텀시트 + 적용 버튼 방식
- 우선순위: 상

---

#### 3) 고양이 상세 페이지

- 고양이 사진
- 상태 (보호중/종료)
- 공고 종료일 + D-day
- 성별 / 나이 추정
- 보호소 정보
- 발견 장소(지역)
- 우선순위: 상

---

#### 4) 이미지 확대 보기

- 사진 클릭 시 전체 화면
- 모바일 감상 최적화
- (핀치 줌은 후순위)
- 우선순위: 상

---

#### 5) 공유 기능

- 카카오톡 공유 (1순위)
- 링크 복사 (fallback)
- 상세 페이지 링크 공유
- 동적 OG 이미지 생성
- 우선순위: 상

---

#### 6) 찜 기능

- 로그인 없이 사용
- 로컬 저장 기반
- 찜 목록 페이지 제공 (animal id만 저장)
- 우선순위: 중

---

#### 7) 서버 프록시 및 캐시 (BFF)

- 공공 API는 브라우저에서 직접 호출하지 않고 Next 서버(Route Handler)에서만 호출한다
- 서비스키는 서버 환경변수에만 둔다 (`NEXT_PUBLIC_` 금지)
- API가 정렬을 지원하지 않아, 서버가 전체 수집 → 캐시 → 정렬/필터/커서 자르기를 담당한다
- 우선순위: 상

---

### 4.2 후순위 기능 (명시만, MVP 미포함)

- 이미지 핀치 줌
- SNS 공유 확장 (Instagram, X)
- 공유 문구 자동 생성(AI/룰 기반)

## 5. URL & 상태 관리 정책

### 5.1 URL 규칙

- 목록: `/animals`
- 상세: `/animals/{id}`
- 찜: `/favorites`

### 5.2 Search Params (목록)

- `species`: cat | dog
- `region`
- `status`: protected | ended | all (기본 `protected`)
- `sort`: latest | endingSoon

> 필터/정렬 상태는 **URL Search Params가 Single Source of Truth**
>
> `page`는 URL에 넣지 않는다. 무한스크롤의 내부 커서로 관리한다.

## 6. 기술 스택 & 아키텍처 원칙

### 6.1 기술 스택

- Framework: Next.js (App Router)
- Data Fetching: TanStack Query
- Styling: Tailwind CSS + shadcn/ui
- Validation: Zod (외부 DTO 검증 only)
- Storage: localStorage
- Share: Kakao Share SDK
- OG Image: Next.js 동적 OG 이미지
- Server Layer: Next.js Route Handler (공공 API 프록시, 서버 캐시)

---

### 6.2 아키텍처 원칙 (Hexagonal + FSD)

- 공공 API는 외부 세계(Outside)로 격리한다
- 브라우저는 공공 API를 직접 호출하지 않는다 (서버 경유)
- 서버와 클라이언트는 Domain을 공유하지 않는다. 사이에 별도 응답 DTO(계약)를 둔다
- 외부 응답은 DTO로만 존재한다
- DTO는 Zod로 검증 후 Mapper를 통해 Domain으로 변환한다
- UI는 Domain 모델만 소비한다
- Core는 Port(인터페이스)에 의존한다
- pages는 레이아웃과 배치만 담당하며 비즈니스 로직을 갖지 않는다
- URL을 상태 관리의 중심으로 사용한다
