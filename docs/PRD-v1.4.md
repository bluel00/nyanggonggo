# PRD v1.4 변경분 – 상세에서 뒤로가기

## 0. 문서 정보

- 버전: v1.4 (초안, 2026-10-14)

## 1. 왜

- EL이 써 보다가 겪었다: 공유 링크로 상세에 들어와 화면 안 뒤로가기를 누르면, 목록이 그 공고의 지역으로 좁혀져 있었다. 그 지역이 다음에 들어와도 남아 있었다.
- 조사(코드 읽기, 2026-10-14):
  - 지역으로 좁히는 건 PRD-v1.1에서 정한 동작이다(focus: 그 공고의 지역 목록 + 그 카드로 스크롤).
  - 지역을 저장하는 건 의도가 아니다. 뒤로가기 자체는 기억(쿠키)을 쓰지 않는다. 남은 경로는 추측이다: 좁힌 목록에서 필터 시트 적용하기를 누름, 또는 같은 주소가 다시 열림.
  - 목록에서 들어온 경우에도 상세에서 새로고침하면(카카오톡 공유를 다녀오며 브라우저가 탭을 다시 불러오는 경우 포함) 화면 안 뒤로가기가 원래 목록이 아니라 좁힌 목록으로 간다. "목록을 거쳤다" 표시가 새로고침하면 사라지는 메모리 변수이기 때문이다.
- 요건을 다시 정했다: 공유로 들어온 사람에게 받은 카드를 목록 안에서 보여 주는 것은 중요하지 않다. 중요한 것은 목록을 보던 사람이 상세에 다녀와도 보던 자리로 돌아가는 것, 그리고 공유 링크가 내 설정을 바꾸지 않는 것이다.

## 2. 지금 동작 (확인된 사실)

- 서버가 (축종, 시·도, 시·군·구) 조합의 전체 목록을 공공 API에서 500건씩 모두 받아, 상태 필터·정렬·페이지 나누기를 직접 한다. 공공 API 페이지 단위로 서버 캐시(300초 재검증)에 둔다.
- 앱에는 20건씩, 앞 페이지 마지막 카드 기준 커서로 준다. 앱은 `useInfiniteQuery` 하나에 페이지를 쌓는다. `gcTime` 5분, 다시 받기 없음, 페이지 수 상한 없음.
- 목록 → 상세 → 뒤로가기: 캐시가 살아 있으면 쌓인 페이지가 그대로 보이고, 열었던 카드 id로 스크롤을 되돌린다(E2E `list-scroll`, `list-refetch`로 확인됨).
- 기억되는 설정: 쿠키 두 개(`nyanggonggo.region`, `nyanggonggo.species`, 1년). 쓰는 곳은 필터 시트 적용하기(지역·축종)와 홈 선택(축종)뿐이다.
- `/`의 동작: 축종 쿠키가 없으면 `/home`, 있으면 쿠키의 축종·지역 목록(지역 쿠키가 없으면 서울).

## 3. 요구사항

### R1. 목록 → 상세 → 뒤로가기: 보던 자리로 돌아간다

- 앱 안에서 목록을 거쳐 상세에 왔으면, 화면 안 뒤로가기와 브라우저 뒤로가기 모두 원래 목록 주소로 돌아간다.
- "목록을 거쳤다"는 표시는 새로고침해도 남아야 한다(같은 탭 안에서만, 세션 저장소).
- 쌓인 페이지는 30분까지 앱 메모리에 남는다(`gcTime` 5분 → 30분). 그 안에 돌아오면 다시 받지 않고, 스켈레톤 없이, 열었던 카드가 화면 안에 보인다.
- 새로고침이나 탭 재로딩 뒤에는 원래 목록 주소로는 돌아가지만, 1페이지부터 다시 받을 수 있다(보던 자리는 보장하지 않음). 이 경우를 줄일지(쌓인 페이지를 세션 저장소에 보관)는 폰에서 써 본 뒤 정한다.
- 알려진 빈틈: 새로고침한 상세가 아직 로딩 화면일 때 뒤로가기를 누르면 원래 목록이 아니라 `/`로 간다. 페이지가 활성화되기 전에는 버튼이 단순 링크(`/`)로 동작하기 때문이다. 로딩이 끝난 뒤에는 원래 목록으로 간다.

### R2. 공유 링크 → 상세 → 뒤로가기: 내 평소 화면으로 간다

- 목록을 거치지 않고 상세에 들어왔으면, 화면 안 뒤로가기는 `/`로 간다. 처음 온 사람은 홈(축종 선택), 이미 쓰던 사람은 자기 설정 목록의 맨 위다.
- 공유 링크로 들어온 상세와 그 뒤로가기는 기억된 설정(쿠키)을 바꾸지 않는다.
- 지역으로 좁힌 목록과 받은 카드 초점(focus)은 없앤다.
- 로딩 화면(스켈레톤)의 뒤로가기도 같다. 공고를 몰라도 갈 곳이 정해져 있으므로 버튼을 보인다(PRD-v1.3 6절 '로딩 뼈대의 뒤로가기' 결정을 대체).

## 4. 완료 기준

| 기준 | 확인 방법 |
|---|---|
| 목록(5페이지까지 내림) → 상세 → 화면 안·브라우저 뒤로가기: 요청 0건, 스켈레톤 없음, 열었던 카드가 화면 안 | E2E |
| `gcTime`이 30분 | 단위 테스트(설정값). E2E는 타이머를 옮길 수 없어 검사하지 않는다 |
| 목록 → 상세 → 새로고침 → 화면 안 뒤로가기: 원래 목록 주소(쿼리 포함)로 감 | E2E |
| 공유 링크 직접 진입 → 화면 안 뒤로가기: 쿠키 없으면 `/home`, 있으면 쿠키의 축종·지역 목록 | E2E |
| 공유 링크 직접 진입 → 로딩 화면에서 뒤로가기: `/`로 감, 쿠키 그대로 | E2E |
| 위 경우 모두 쿠키 값이 바뀌지 않음 | E2E |
| focus 관련 코드·테스트·문서가 남지 않음 | 검색으로 확인 |

## 5. 비범위

- 최근 본 아이(쿠팡의 최근 본 상품 같은 기능): 별도 기능, 백로그
- 쌓인 페이지를 세션 저장소에 보관: R1 적용 후 폰에서 써 보고 정한다
- 깊이 내려간 목록을 되돌릴 때 다시 그리는 비용(architecture 12절 (B)): 관찰
- 데이터 갱신 주기(5분 캐시 대신 몇 시간·하루 단위): 백로그. 정하려면 실제로 얼마나 바뀌는지부터 잰다
- 필터 시트 적용하기가 바꾸지 않은 항목까지 저장하는 문제: focus를 없애면 좁힌 목록이 사라져 생길 일이 거의 없다. 다시 재현되면 연다
- 찜 화면에서 공고 하나의 HTTP 오류가 화면 전체를 에러로 만드는 문제(architecture 12절 53)

## 7. 결정 기록

| 항목 | 결정 | 이유 |
|---|---|---|
| 공유 링크 뒤로가기 | `/`로 (처음 온 사람 홈, 쓰던 사람 자기 설정 목록) | 받은 카드를 목록에서 보여 주는 것은 요건이 아니다. 내 설정을 바꾸지 않는 것이 중요하다(EL) |
| focus | 없앤다 | 지역이 바뀌는 불편의 원인. 코드가 단순해진다 |
| "목록을 거쳤다" 표시 | 메모리 변수 → 세션 저장소 | 새로고침 뒤 좁힌 목록으로 가던 문제의 근본 원인 |
| 쌓인 페이지 보관 | `gcTime` 30분, 세션 저장소 보관은 보류 | 가장 작은 변경부터. 탭 재로딩이 잦은지 써 보고 정한다 |
| 받은 카드를 목록 맨 위에 고정, 양방향 스크롤 | 하지 않는다 | 요건이 아니다. 양방향은 공공 API에 위치 조회가 없어 비용이 크다 |
| 문서 | 새 변경분 PRD-v1.4 | v1.2·v1.3과 같은 방식 |
| 로딩 화면 뒤로가기 | 상세와 같게(앱 안에서 왔으면 뒤로, 아니면 `/`) | 대체 이동이 공고를 몰라도 되게 바뀌었다. v1.3 결정 대체 |
